A

核心判斷

現況不是完整 compiler

JumpJet 現在只有字元 Reader、少量 Token 編號、瀏覽器 demo。Lexer、Parser、Semantic、IR、VM、Optimizer、Codegen 都還沒有實作。

建議先做「快而清楚的 bytecode compiler」。前端保持單向資料流。中段用緊湊 IR。後端先接 bytecode VM，再用 benchmark 決定是否增加 JavaScript 或 WebAssembly codegen。

B

現有執行路徑

main.html 是啟動殼。reader.js 同時承擔 input abstraction、demo、輸出與 token 定義，因此還沒有可獨立測試的 compiler 邊界。

已有與缺口

階段 現況 下一個可驗收產物
Source reader ✓可逐字讀取與回退 span 與位置追蹤
Lexer ✗尚未實作 token kind/start/end 陣列
Parser ✗尚未實作 Pratt expression parser + statement parser
Semantic ✗尚未實作 scope、symbol、type/error table
IR / Optimizer ✗尚未實作 bytecode 或 SSA-lite IR
Backend ✗尚未實作 bytecode VM；之後才評估 JS/Wasm
D

建議的目標架構

每一層只接受上一層的資料結構。錯誤資訊另走 diagnostics side table。這樣可避免 AST 節點混入 UI、log 或 jQuery 狀態。

E

「高速」先拆成兩個指標

目標 主要瓶頸 優先策略 建議基準
編譯快 allocation、substring、重複掃描 索引 span、數字 kind、單向 pass、重用 buffer MB/s、allocations、p50/p95 latency
產物跑得快 dispatch、boxing、dynamic lookup bytecode specialization、inline cache、typed value slots ops/s、warmup、steady-state
啟動快 模組與 runtime 體積 小 runtime、延遲載入 optimizer cold-start time、bundle bytes
不要用「感覺快」驗收

每個階段保留 correctness corpus。效能測試使用固定輸入大小，分開量 lexer、parser、emit 與 execute。

F

JavaScript 熱路徑規則

  • Token 只存 kind/start/end。需要文字時再從 source 切片。
  • Token kind 使用連續整數。大量資料可放 Uint16Array 與 Uint32Array。
  • AST 節點維持固定欄位順序。不要在熱路徑動態新增 property。
  • Parser 使用索引前進。避免 shift()、正則回溯與每字元 callback。
  • 常見 opcode 放在 VM dispatch 的短路徑。冷門 diagnostics 放到旁路。
  • 先 profile，再做 object pool、arena 或 opcode fusion。

H

演進順序與決策點

  1. 1切出 Core API移除 reader.js 對 DOM 與 jQuery 的依賴；加入 Node 測試
  2. 2Lexer定義 TokenKind、位置與 diagnostics；用 corpus 驗證
  3. 3Parser先做小語法與 AST；加入 precedence 與 recovery
  4. 4Semantic + IR建 scope/symbol；lower 到小型 bytecode
  5. 5VM完成端到端 compile/run；建立 correctness baseline
  6. 6Profile找出真實熱點；只優化有量測證據的階段
  7. 7第二 backend依產品目標選 JavaScript codegen 或 WebAssembly

開始實作前要定三件事：輸入語言是什麼、輸出目標是什麼、速度指的是 compile time 還是 runtime。這三個答案會決定 AST、IR 與 backend。
