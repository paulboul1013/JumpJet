B

真正的入口與模組責任

瀏覽器的 compileAndRun 呼叫公開的 compile，再呼叫 run。 compile 依序執行各 phase，遇到 diagnostics 就返回。 run 直接委派 execute。

模組 擁有的責任 對後續階段的承諾
lexer 字元、關鍵字、最長運算子辨識 tokens 附來源範圍
parser precedence、associativity、statement 結構 syntax AST 保留名稱
analyzer scope、const、初始化檢查、slot 分配 bound AST 的識別字已換成 slot
compiler 指令選擇、stack 配平、jump 回填 產生可供 VM 執行的 program
VM program 邊界檢查與指令執行 對合法程式返回值

這些依賴沒有形成循環。 compiler 不重做名稱查找，VM 也不依賴 AST 或 DOM。 這是目前設計最值得保留的部分。

依據：公開入口、瀏覽器入口，第 95 行、analyzer、compiler。

C

Bytecode 與執行狀態

program 有 version、constants、code 與 slotCount。 code 是平坦的 JavaScript number array，沒有二進位編碼。 共有 21 個 opcode，使用零個或一個 operand。 jump target 是 code array 的絕對 index。

每次 execute 都建立自己的 operand stack、slots 與 initializedSlots。 instructionPointer 指向下一個待讀位置。 各次執行沒有共用 VM 可變狀態。

例如，賦值先產生值，再 Duplicate，最後 StoreSlot。 StoreSlot 取走副本，原值保留作為賦值運算結果。 一般 expression statement 用 Pop 丟棄結果。 最後一個頂層 expression statement 用 Return 返回結果。

analyzer 為每個宣告分配唯一 slot，離開 block 不回收。 目前沒有函式呼叫、call frame、closure 或物件 heap。 數值運算直接使用宿主 JavaScript 的運算子。 目前也尚未 self-host。

依據：opcode 定義、指令生成，第 69 行、執行狀態，第 30 行、現行規格。

D

語意層有兩個可重現問題

優先修正：內層宣告前的引用會綁到外層

let value = 1;
{
	value = 2;
	let value = 3;
}
value;

JumpJet 成功編譯並返回 2。 同一段程式在 Node 會因 TDZ 拋出 ReferenceError。 analyzer 在走到宣告時才加入 binding。 因此，前面的賦值會解析成外層 slot。

最小修正是進入 scope 時先收集該 scope 的直接宣告。 所有 binding 起初都標成未初始化。 接著依序分析 statement，並更新初始化狀態。 這項責任應留在 analyzer。

現行規格明文描述 initializer 自我引用的 TDZ。 上述案例揭露的是與 JavaScript block scope 的語意落差。 規格也需要補上整個 block 的宣告可見範圍。

依據：resolve，第 37 行、宣告建立，第 129 行、block traversal，第 169 行。

接著修正：關鍵字表讀到 Object prototype

let constructor = 1; constructor; 會編譯失敗。 toString 作為變數名稱也會失敗。 keywords 是一般 object，查找會讀到繼承的屬性。 Object.freeze 不會移除 prototype。

改用 Map，或用 Object.hasOwn 限制查找自己的 key。 這是 lexer 的責任，parser 不需要繞過錯誤 token。

依據：keywords 定義，第 53 行、查表，第 148 行。

E

VM 邊界驗證仍不完整

Jump target 只檢查範圍

下面的 program 返回 42。 線性解碼的指令起點是 0、2、4、6。 target 5 指向 Constant 的 operand，VM 卻把它當作 Return。

{
	version: 1,
	constants: Array(9).fill(42),
	code: [0, 0, 20, 5, 0, 8, 8],
	slotCount: 0
}

目前 compiler 產生的 jump 不會觸發這個案例。 缺口在公開 run 接受任意 program 的邊界。 最小修正是先解碼指令，再檢查 target 是否為指令起點。 code.length 作為 target 的既有政策可另行保留。

稀疏 constants 會讓 undefined 進入 VM

constants 為 new Array(1) 時，forEach 會跳過空洞。 Constant 0 因此取得 undefined，Return 也直接返回 undefined。 這違反目前 number 或 boolean 的值域契約。

改用逐 index 驗證，拒絕空洞或不合法的常數。 另外，Return 後方的未知 opcode 目前不會被檢查。 若承諾驗證整個 program，解碼階段就需要檢查不可達指令。 若只承諾檢查執行路徑，文件應明確說明。

依據：constants 驗證，第 17 行、jump 檢查，第 68 行、Constant，第 86 行。

F

執行控制需要明確的邊界

手寫 bytecode 的 Jump 0 會持續執行。 重現腳本由父行程在 750 ms 後終止子行程。 目前來源語法沒有 loop，compiler 也只產生向前跳躍。 因此，這項風險現在主要出現在直接呼叫 run。

瀏覽器在主執行緒同步執行 compile 與 run。 增加 loop 前，建議讓 execute 接受 instruction budget。 若需要使用者中止執行，再把工作移到 Worker。 主執行緒上的 timeout 無法中斷同步 execute。

目前還有可由 source 觸發的問題。 20,000 層括號會讓 compile 拋出 RangeError。 瀏覽器的 try 只涵蓋 run，無法顯示這個編譯例外。 可加入巢狀深度上限，並讓 UI 包住整個編譯執行流程。

依據：VM loop，第 76 行、parser 遞迴，第 106 行、UI 例外邊界，第 95 行。
